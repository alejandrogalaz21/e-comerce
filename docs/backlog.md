# Ticket backlog

> The source of truth for the project's work. Each ticket is implemented as an **OpenSpec change**
> (`/opsx:propose TK-###`): the workflow reads this document, takes the ticket's context, and when
> the change is archived the ticket moves to `closed` with a link to it.
>
> **Categories**: `requirement` = explicitly asked for by the challenge (PDF) · `technical` = a
> necessary project change or debt that the challenge does not ask for.
>
> Convention: the OpenSpec change is named after the ticket's slug (e.g. TK-007 → `products-crud`).

## Way of working

1. Take an `open` ticket → `/opsx:propose TK-### <slug>` (the workflow reads this document).
2. Review the proposal/specs/design/tasks generated in `openspec/changes/<slug>/`.
3. `/opsx:apply` to implement → commits referencing the ticket (`feat: ... (TK-009)`).
4. `/opsx:archive` when done → mark it `closed` here and link the archived change.

Suggested order: TK-011 (integration base) → TK-007 + TK-013 (CRUD + migrations) → TK-008 (search)
→ TK-009 + TK-023 (CSV import + validations) → TK-012 (seed) → TK-010 + TK-022 (orders + fake
payment) → TK-014/015 (hardening, cross-cutting) → TK-016 (tests) → TK-017 (README).
